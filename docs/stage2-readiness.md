## Deadline / HOLD

`stage2_guard.supervise` implements the parent decision boundary using an injected, already-dormant contained worker. Start signals verification rather than performing unbounded worker creation. The monotonic total window covers validation, work, termination acknowledgement, handle cleanup and journal publication; two seconds are reserved for cleanup by default. API work must happen in that separate worker, never block the parent. The current PR accepts only synthetic workers; the concrete dormant-worker IPC-to-native port is implemented but disabled; its worker provisioning/factory is NOT supplied or activated. Consequently this is not proof of a hard real-Windows wall bound and does not by itself authorize Stage 2.

An immutable start record prohibits restoration before work. On failure/HOLD the parent records an immutable HOLD before termination attempts, never deletes reservations, and preserves fail-closed state even when termination succeeds later. The start intent commits only the hash of a random machine-completion capability. The token is returned only after all deadline checks pass; a separate post-return publish_success audit commit is mandatory. A late termination record plus failed HOLD publication cannot produce that commit. This token is not a human signature. If writing HOLD fails, an incomplete successful-return protocol still denies restoration. Cleanup late/failure also HOLDs. No machine result grants automatic restoration; a separate on-site exit-check acknowledgement is mandatory. The positive journal alone is never a restoration authority. Blocking/failed storage or OS calls are not treated as real-time guarantees.

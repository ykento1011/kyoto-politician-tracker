議会のミカタ：新規都市追加・水平展開 標準運用手順書 (SOP)
改訂: 2026年10月（生発言テキスト統一・原本直結・セマンティック公約評価パイプライン導入）
=======================================================================

【基本原則】

1. 設定駆動（Config-driven）アーキテクチャとProps伝搬の徹底
   - 都市固有の名称・カラー・URL・ファイルパス・SEOメタタグは設定ファイル（`frontend/src/config/cities.js`）および都市アダプターに集約する。
   - コンポーネント内部やユーティリティ関数（リンク生成等）に都市名やテナント名をハードコード（直書き）してはならない。
   - 下層コンポーネントや関数を呼び出す際は、必ず `cityCode` をPropsや引数としてバケツリレー（伝搬）させること。二者択一の三項演算子（例: `isOsaka ? 'osaka' : 'kyoto'`）やデフォルト引数（`='kyoto'`）への甘えは厳禁。
   - すべてのデータJSONのフェッチは `getCityDataUrl(cityCode, 'ファイルキー')` を経由して行う。

2. 一次情報至上主義と会議録ディープリンク完全保証（Zero-Hallucination & Deep Link Gate）
   - 二次解説や推測によるデータ登録を一切禁止し、自治体公式Web・市会公式・選管公式PDF・原本公文書のみを情報源とする。
   - 会議録への直リンクは「個別会議・発言のPC版ビュー（MinuteView.html）」を絶対原則とし、検索トップ（MinuteSearch.html / SpMinuteSearch.html）への安易な逃げやハードコードを厳禁とする。
   - スマートフォン版URL（SpMinuteView.html）は外部直接参照時に403エラーを誘発するセキュリティ仕様が存在するため、必ずPC版パーマリンク（MinuteView.html?council_id=...&schedule_id=...）を採用する。

3. 生発言（肉声）優先・三人称要約の根絶原則【超重要・都市間対称性】
   - トピック詳細画面（政策論戦マップ）や発言カードに表示するテキストは、AIによる三人称要約文（「議員は〜について質問し、行政側が〜答弁した」）を排し、タイムライン原本の【議員本人の実際の発言本文（statement_text / 肉声）】を最優先で格納・表示する。
   - 京都・大阪・名古屋など、閲覧する都市によって表示形式（生発言か要約文か）に非対称性・乖離を生じさせてはならない。

4. UIモーダル連携の単一ロジック化・原本レコード直結原則
   - トピック詳細画面（`TopicDetailPage.jsx`）において、手動でプロパティを再構成した不完全なオブジェクトをモーダルに渡してはならない。
   - 議員詳細画面（`SpeakerDetailView.jsx`）や一覧カード（`ThreadCard.jsx`）と全く同一の質疑レコード解決ロジック（`handleViewExchangeContext`）に統一し、原本データベース（`statements_summary.json`）の完全なレコードを `onViewContext(stmt)` に直接引き渡す。

5. 行政理事者（局長・部長等）発言の完全排除と議員質疑への正規化
   - 政治家トラッカーは市民の代表である議員（および市長）を追跡するシステムである。
   - 行政側の局長・理事者（例:「西島副首都」「丸山大阪」「○○局長」等）の答弁・説明発言が単独で「議員質問」としてトピックカードに混入することを厳禁とし、同一会議でその質疑を行った本来の正規議員レコードへ置換、またはカードを除外する。

6. 単一パイプライン・アダプター原則（No-Copy-Paste Pipeline）【厳格遵守】
   - 都市ごとにパイプラインスクリプトを複製（コピペ）することを物理的に禁止する。
   - パイプラインはすべて `data-pipeline/` に集約し、`pipeline/` のような別名フォルダの並立を禁止する。
   - LLM評価プロンプト、8大政策カテゴリ、4軸整数スコア、キーワード、並列処理は単一の共通コア（run_unified_pipeline.py）で集中管理する。
   - トピック要約（マクロ論戦マップ）も単一の共通ジェネレーター（generate_unified_topic_summaries.py）で集中管理する。
   - 都市ごとの差異（BigQueryクエリ、行政側役職判定、名寄せ、スレッド化ロジック）は「都市アダプター（{City}Adapter）」クラスとしてのみ実装する。

7. 全自動インテグリティ監査（Automated Integrity Audit）の必須化
   - 手動による目視確認には限界がある。新都市追加・データ更新時は、全トピック・全発言カードを網羅走査する検証スクリプト（`audit_unified_integrity.py`）を実行し、【モーダル到達率 100%（全件完全到達）】および【生発言率 90%以上】が機械的に証明されるまでデプロイを許可しない。

8. 評価スキーマ・キー互換の完全原則（京都マスター準拠）
   - いかなる都市であっても、以下の仕様を勝手に改変してはならない。
     - 政策カテゴリ: 京都マスターの「8大政策カテゴリ」固定（都市計画・その他等の独自分類禁止）。
     - 4軸スコア: 各1〜5の【整数値（int）】（1.0〜5.0等の小数は禁止）。
     - 分析メモ（キー互換）: フロントエンドとの互換性を保つため、`reasoning` と `scoring_reasoning` の【両方のキー】に同一テキストを二重出力する。
     - 発言順序（Sequence Number）: フロントエンドのタイムライン取得に必須。`sequence_number` プロパティを確実にJSONに含めるか、`id` から抽出できる設計にする。
     - 会議録直通URL（official_url）: BigQueryの `meetings.url` から取得した正規の `MinuteView.html` URLを、発言スレッドおよび要約JSONに漏れなく格納する。
     - キーワード（keywords）: 必須。3件の配列。

9. 【NEW】セマンティック照合による客観的公約評価（Zero-Hallucination Matching）
   - 公約トラッカーの判定において、手動による恣意的なキーワード紐付けや主観的解釈を完全に排除する。
   - `gemini-embedding-2` によるベクトル類似度計算を用い、コサイン類似度 `sim >= 0.65`（中精度以上）を明確な境界線として完全自動・客観的に照合を行う。

Phase 1: 事前適合性診断と自治体ID・会議録テナントの確定
-----------------------------------------------------------------------

1. 自治体ID（governing_body_id）マスタ
   BigQuery抽出時に用いる公式自治体IDを確認・確定する。
   - 京都市会: 88 / 大阪市会: 532 / 名古屋市会: 958 / 横浜市会: 1249 / 神戸市会: 156

2. 会議録システムとDiscussNetテナント識別子マスタ【超重要】
   NTT-AT DiscussNet系（`ssp.kaigiroku.net/tenant/<テナントID>/`）の正式識別子を厳密に確認する。
   - 京都市会: `kyoto`
   - 大阪市会: `cityosaka`（※`osaka` は無効／404）
   - 名古屋市会: `nagoya`

3. 会議録パーマリンクの動作検証
   - `MinuteView.html?council_id=...&schedule_id=...` 形式でブラウザから外部直アクセスし、セッションエラー（403/404）なく議事録が開くことを確認する。
   - BigQueryの `meetings` テーブルの `url` カラムに、この形式のURLが既に正しく格納されているか確認する。

4. 採決結果（議決データ）公開形式の特定
   - 電子採決（HTMLテーブル形式）: 議員個人の賛否が記録されており、機械的抽出が可能。
   - 起立採決（会派別賛否＋例外ト書き）: 「市会だより」等の会派ごとの賛否テーブルと、造反・退席・除斥議員を例外適用して個人賛否を復元する。

Phase 2: 一次資料Deep Research・公文書検証ゲート【必須品質ゲート】
-----------------------------------------------------------------------

1. 首長公約マニフェスト原本の取得・項目抽出
   - 外部メディアの要約記事ではなく、選挙公報原本または首長公式サイトの政策集のみを採用する。

2. 首長トラッカーのデータ構造とピンポイントURL検証
   - データ構造の確認: マイルストーンが配列（`milestones: [...]`）か、単一オブジェクト（`milestone: {...}`）かを必ずプロファイリングする。
   - トップページ逃げの禁止: 沿革一覧や検索トップでお茶を濁さず、対象事象に1対1で合致する公文書URLを特定して結合する。

3. 対立議案・賛否が割れた議案（Contested Bills）の抽出
   - 直近任期（4年間）の本会議議決一覧から、全会一致以外の案件を全件抽出し `{cityCode}_votes_summary.json` に整形する。

4. 議員マスタの公式選管・市会名簿照合
   - 市会公式名簿から、現職議員全員の「氏名」「所属会派」「選挙区」を抽出し、名寄せ辞書（`ALIAS_MAP`）を整備する。

Phase 3: 都市アダプター実装・データ抽出とJSON出力
-----------------------------------------------------------------------

1. 会議録生データの構造プロファイリング
   - 行政側（市長、副市長、局長等）と議員の役職キーワードリストを作成し、答弁者を正確に除外・識別する。

2. プレースホルダーJSONの先行配置
   - 開発中、Viteが404 HTMLを返してアプリがクラッシュするのを防ぐため、空の配列 `[]` を持ったJSONを事前に配置する。

3. 都市アダプターの実装（`run_unified_pipeline.py` 内）
   - `fetch_data()`: BigQueryクエリで必ず `m.url AS official_url` を取得すること。
   - `build_threads()`: 各スレッドには質問開始発言の `sequence_number` と `official_url` を漏れなく出力すること。

4. 質疑・答弁タイムラインの生成（`build_timeline_contexts.py`）
   - 各スレッドの質問開始から答弁終了まで、最大12発言程度のバッファを持たせて抽出。

5. 統一トピック要約（政策論戦マップ）の生成（`generate_unified_topic_summaries.py`）
   - 生発言本文の優先格納: `summary` ではなく `statement_text` から挨拶等の定型句をトリムしてカードテキストに格納する。
   - トピックキーワード誤爆の防止: 「津波避難」単体ではなく「津波避難ビル」「防潮堤」等の複合語でスコアリングし、無関係な質疑の混入を防ぐ。


-----------------------------------------------------------------------
Phase 4: データ取得フック層の改修（useStatements.js）
-----------------------------------------------------------------------

1. Supabaseフォールバックの都市制限:
   - Supabaseによるデータ取得は `cityCode === 'kyoto'` のみに限定し、データ漏洩（Data Bleed）を完全に遮断する。

2. 発言番号の堅牢化:
   - JSONデータ内に `sequence_number` が存在しない場合、`stmt.id`（例:`th_5336591_85`）の末尾から数値を抽出するフォールバックを実装する。

3. 議員マスタの無条件・常時フェッチ（超重要）:
   - 質疑ログのフェッチ成否に関わらず、`speaker_stats.json` は【常時・無条件】でフェッチして動的集計にマージする。

4. 姓名の表記揺れ・スペース耐性:
   - `masterMap` には原名とともに `replace(/\s+/g, '')` を適用したスペース除去キーも同時に登録して照合する。

Phase 5: フロントエンド統合とURLパーマリンク完全標準化
-----------------------------------------------------------------------

1. 会議録リンクユーティリティ（`officialLink.js`）の標準化仕様
   - 以下の【優先度付きフォールバックチェーン】でURLを解決する：
     `stmt.official_url || stmt.source_url || stmt.url || stmt.doc_url || stmt.evidence_url || ''`
   - `MinuteSearch.html` は自動的に `MinuteView.html` へ補正・置換する。

2. `TopicDetailPage.jsx` の原本レコード解決ロジック標準化
   - `App.jsx` から `TopicDetailPage` に `statements={statements}` と `onViewContext={handleViewContext}` を必ず渡す。
   - `handleViewExchangeContext` は、カードから渡された情報を元に `statements` 原本配列から完全なレコード（`meeting_id`, `sequence_number` 入り）を探索し直してからモーダルを開く。

3. 発言カードの2連アクションボタン標準化
   - 各発言カード下部に、「公式原本で確認」と「会議録・質疑の文脈を見る →」の2ボタンを並列配置する。

Step 1. 質疑 Embedding キャッシュの差分生成
新しく追加された質疑のみを自動検知し、ベクトルを事前計算してキャッシュに追記する。
※API制限対策のため、中断レジューム機能が自動で働く。

Step 2. 統一公約トラッカーのビルド
公約ベクトルと質疑ベクトルのコサイン類似度照合を行い、フロントエンド用 JSON を出力する。
判定閾値は原則 sim >= 0.65（文脈合致・同義語レベル）を維持し、不用意に引き下げてノイズを誘発しないこと。

更新された全データについて、ノイズ疑い（低精度結合）が混入していないかを一括検証する。

PowerShell

【トラブルシューティング・チェックリスト（実戦教訓）】
=======================================================================

| 現象 | 主な原因 | 対処法 |
| :--- | :--- | :--- |
| 京都は生発言なのに大阪・名古屋は要約文が表示される | `generate_unified_topic_summaries.py` で `summary` を代入していた | `statement_text`（生発言本文）を最優先で取得・格納するよう統一し、定型句をトリムして再生成する |
| 防災トピックに「民泊」など全く無関係な質疑が混入する | キーワードに「津波避難」などの端緒単語が含まれ誤爆した | キーワードを「防潮堤」「浸水想定区域」等の主題複合語に厳格化してトピック生成を再実行する |
| トピック詳細カードをクリックしてもモーダルが開かない① | `App.jsx` から `TopicDetailPage` に props が伝搬していない | `<TopicDetailPage statements={statements} onViewContext={handleViewContext} />` を確実に渡す |
| トピック詳細カードをクリックしてもモーダルが開かない② | `TopicDetailPage.jsx` が不完全な独自オブジェクトを作って渡している | `SpeakerDetailView` と完全同一の `handleViewExchangeContext`（原本レコード探索）に統一する |
| 発言カードに「西島副首都」などの行政局長名が表示される | 行政理事者の説明・答弁発言が誤って議員質問として抽出された | 局長・理事者の役職名を検知し、同一会議録内の正規議員の質疑レコードへ置換するかカードを除外する |
| 「公式原本で確認」が会議録検索トップに飛ばされる | `officialLink.js` が `source_url` のみを参照し `official_url` を無視していた | `stmt.official_url || stmt.source_url` の優先度チェーンに変更し、MinuteSearchをMinuteViewへ置換する |

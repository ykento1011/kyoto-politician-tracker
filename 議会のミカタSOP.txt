=======================================================================
議会のミカタ：新規都市追加・水平展開 標準運用手順書 (SOP)
改訂: 2026年10月（多層サーキットブレーカー必須化・SSoTマスター先行配備・run_update自走統合基準・3段階インテグリティ監査標準化）
=======================================================================

【基本原則】

1. 設定駆動（Config-driven）アーキテクチャとProps伝搬の徹底
   - 都市固有の名称・カラー・URL・ファイルパス・SEOメタタグは設定ファイル（frontend/src/config/cities.js）および都市アダプターに集約する。
   - コンポーネント内部やユーティリティ関数に都市名やテナント名をハードコード（直書き）してはならない。
   - 下層コンポーネントや関数を呼び出す際は、必ず cityCode をPropsや引数としてバケツリレー（伝搬）させる。二者択一の三項演算子（例: isOsaka ? 'osaka' : 'kyoto'）やデフォルト引数（='kyoto'）は厳禁。
   - すべてのデータJSONのフェッチは getCityDataUrl(cityCode, 'ファイルキー') を経由して行う。

2. 一次情報至上主義と会議録ディープリンク完全保証（Zero-Hallucination & Deep Link Gate）
   - 二次解説や推測によるデータ登録を一切禁止し、自治体公式Web・市会公式・選管公式PDF・原本公文書のみを情報源とする。
   - LLM等の推論による公約や政策テキストの自動生成・補完・捏造（ハルシネーション）は絶対厳禁。公約テキストは選管公式選挙公報PDFからの物理的抽出（OCR/テキストパース）および目視による一言一句違わぬ転記のみを許可し、確認できないデータは「白紙（転記待ち）」とする。
   - 会議録への直リンクは「個別会議・発言のPC版ビュー（MinuteView.html）」を絶対原則とし、検索トップ（MinuteSearch.html / SpMinuteSearch.html）への逃げを厳禁とする。
   - スマートフォン版URL（SpMinuteView.html）は外部直接参照時に403エラーを誘発するため、必ずPC版パーマリンク（MinuteView.html?council_id=...&schedule_id=...）を採用する。

3. SSoTマスター先行配備と多層サーキットブレーカー原則【2026-10 新設・最優先防護】
   - 議事録抽出や公約結合に先立ち、必ず議員名簿・現職首長・会派の正本（Single Source of Truth）を確定させる。
   - 自治体サイトの構造変更やパース失敗によるデータ破損を防ぐため、以下の多層サーキットブレーカーをスクレイパーに必須配備する：
     ① 首長照合ガード: 自治体公式トップと mayors.json の首長名が不一致の場合、即座に安全停止（exit 2）。
     ② 定数上下限ガード: 取得件数が 定数 × 0.95 未満、または定数超過の場合は即座に安全停止（exit 1）。
     ③ 会派充足率ガード: 無所属率が50%を超えた場合は会派パース異常と判定し、前回の正常会派を自動保護（フォールバック）。
     ④ ノイズサニタイザー: 氏名文字数（2〜8文字）、日本語文字（漢字・かな）必須、多言語UI文字列（Language, Page等）の自動除外。

4. 議員動態オートヒーリングと過去質疑ログの完全保護原則
   - 名簿から外れた議員は物理削除せず、is_active: false / status: "retired" として論理保持する。
   - sync_master_data.py において、退任議員も有効発言者マップ（valid_speaker_map）に保持し、過去任期の発言ログ（statements_summary.json）が誤って削ぎ落とされるのを防ぐ。
   - 手動修正が必要な場合は manual_overrides_{cityCode}.json に記述し、スクレイピング結果より最優先で上書き適用する。

5. 生発言（肉声）優先・三人称要約の根絶原則【都市間対称性】
   - トピック詳細画面（政策論戦マップ）や発言カードに表示するテキストは、AIによる三人称要約文（「議員は〜について質問し、行政側が〜答弁した」）を排し、タイムライン原本の【議員本人の実際の発言本文（statement_text / 肉声）】を最優先で格納・表示する。
   - 都市によって表示形式（生発言か要約文か）に非対称性・乖離を生じさせてはならない。

6. UIモーダル連携の単一ロジック化・原本レコード直結原則
   - トピック詳細画面（TopicDetailPage.jsx）において、手動でプロパティを再構成した不完全なオブジェクトをモーダルに渡してはならない。
   - 議員詳細画面（SpeakerDetailView.jsx）や一覧カード（ThreadCard.jsx）と全く同一の質疑レコード解決ロジック（handleViewExchangeContext）に統一し、原本データベース（statements_summary.json）の完全なレコードを onViewContext(stmt) に直接引き渡す。

7. 行政理事者（局長・部長等）発言の完全排除と議員質疑への正規化
   - 政治家トラッカーは市民の代表である議員（および市長）を追跡するシステムである。
   - 行政側の局長・理事者（例:「西島副首都」「丸山大阪」「○○局長」等）の答弁・説明発言が単独で「議員質問」としてトピックカードに混入することを厳禁とし、同一会議でその質疑を行った本来の正規議員レコードへ置換、またはカードを除外する。

8. 単一パイプライン・アダプター原則（No-Copy-Paste Pipeline）
   - パイプラインはすべて data-pipeline/ に集約し、スクリプトの複製（コピペ）や場当たり的な一時修復スクリプトの乱立を禁止する。
   - トピック要約（generate_unified_topic_summaries.py）、公約セマンティック結合（build_unified_pledge_tracker.py）、マスター同期（sync_master_data.py）は共通スクリプトで一元管理する。
   - 都市ごとの差異（BigQueryクエリ、行政側役職判定、名寄せ、スレッド化ロジック）は独立したアダプターモジュールとして疎結合に実装する。

9. 3段階全自動インテグリティ監査（Automated Integrity Audit）の必須化
   - 手動による目視確認には限界がある。新都市追加・データ更新時は、以下の3段階監査をパスするまでデプロイを許可しない：
     ① audit_unified_integrity.py: モーダル到達率 98%以上（目標100%）、生発言率 90%以上、行政幹部ノイズ 0件。
     ② audit_pledges_quality.py: 現職議員公約カバレッジ 100%、原本引用率 100%。
     ③ audit_pledge_votes.py: 公約 ⇄ 議案採決（賛否行動）結合の誤爆なし・賛否内訳抽出正常。

10. 公約トラッカー（Pledge Tracker）スキーマの完全対称性原則
    - フロントエンドは議員名をキーとした辞書（Dict/Map）形式（{ "議員名": { ... } }）を前提とする。リスト形式は厳禁。
    - スキーマ（プロパティ名）は全都市完全一致させる：
      - 公約配列キー: tracked_items
      - 公報原文引用: election_promise.quote
      - 関連質疑リスト: council_statements（date, committee, summary, speech_id, official_url）
      - 代表質疑: council_statement（オブジェクトまたは null）
      - 関連議決: council_vote（オブジェクトまたは null）
    - 姓名スペース揺れによる検索空振りを防ぐため、辞書キーには「原名」と「スペース完全除去名」の両方を必ず同一オブジェクト参照として登録する。

11. BigQuery 単一JOINクエリ一括取得の原則（N+1クエリの禁止）
    - 会議一覧（meetings）をループして1件ずつ発言（conversations）をクエリする「N+1クエリ」は通信オーバーヘッドにより取得だけで十数分を浪費するため厳禁とする。
    - conferences -> meetings -> minutes -> conversations を一括で JOIN する単一クエリを発行し、8〜10万件規模の発言であっても数秒でメモリ上に一括展開する設計を必須とする。

Phase 1: 自治体基礎情報・テナント・一次情報源の確定
-----------------------------------------------------------------------

1. 自治体ID（governing_body_id）マスタの確定
   BigQuery抽出時に用いる公式自治体IDを確認する。
   - 京都市会: 88 / 大阪市会: 532 / 名古屋市会: 958 / 横浜市会: 1249 / 神戸市会: 156

2. 会議録システムとDiscussNetテナント識別子マスタの特定
   NTT-AT DiscussNet系（ssp.kaigiroku.net/tenant/<テナントID>/）の正式識別子を確認する。
   - 京都市会: kyoto
   - 大阪市会: cityosaka（※ osaka は無効／404）
   - 名古屋市会: nagoya
   - 横浜市会: 独自ドメイン運用（[http://giji.city.yokohama.lg.jp/tenant/yokohama/](http://giji.city.yokohama.lg.jp/tenant/yokohama/)）

3. 会議録パーマリンクの動作検証
   - MinuteView.html?council_id=...&schedule_id=... 形式でブラウザから外部直アクセスし、セッションエラー（403/404）なく議事録が開くことを確認する。
   - BigQueryの meetings テーブルの url カラムに、この形式のURLが格納されているか確認する。

4. 首長基本情報の確認
   - 現職首長氏名、ふりがな、任期（term / term_start / term_end）、および公式サイト上の公式プロフィールURLを特定する。

5. 議会定数および議決データ公開形式の特定
   - 議会定数（seats）および選挙区一覧を確認する。
   - 採決結果の形式を特定する：
     ① 電子採決（HTMLテーブル形式）: 議員個人の賛否が機械的抽出可能。
     ② 起立採決（会派別賛否＋例外ト書き）: 「市会だより」等の会派別賛否テーブルと造反・退席議員の例外適用で個人賛否を復元。


-----------------------------------------------------------------------
Phase 2: SSoTマスター＆サーキットブレーカー基盤の先行配備【最重要】
-----------------------------------------------------------------------

下流のデータ抽出・生成による汚染を防ぐため、すべての処理に先立ってマスター防護層を構築する。

1. 首長マスター（mayors.json）への登録
   data-pipeline/master/mayors.json に対象都市のエントリを追加する。
   [設定フォーマット]
   "{cityCode}": {
     "name": "首長氏名",
     "hiragana": "ふりがな",
     "term": "2024-2028",
     "term_start": "2024-01-01",
     "term_end": "2027-12-31",
     "official_profile_url": "[https://www.city](https://www.city).../profile.html"
   }

2. 手動オーバーライドファイルの初期配置
   data-pipeline/master/manual_overrides_{cityCode}.json を空の辞書 {} で新規作成する。

3. scrape_councilors_master.py への都市アダプター登録
   - CITY_SPECS に都市名、定数（seats）、任期（term）、市長公式URL（mayor_url）を定義する。
   - scrape_{cityCode}() 関数を実装する：
     - 見出しタグ（<h3>等）と詳細枠のペア走査。
     - <dl>, <dt>, <dd> タグへの完全対応（名古屋市会等の構造欠落防止）。
     - is_valid_councilor_name() サニタイザーによる検証（2〜8文字、日本語文字必須、UI多言語ゴミ遮断）。
     - 定数上下限ガード（定数比 95% <= 取得件数 <= 定数）の自動適用。
     - 会派充足率ガード（無所属率 > 50% で既存会派自動保護）の動作確認。

4. 初回スクレイピングと同期テストの実行
   [実行コマンド]
   python data-pipeline/scrape_councilors_master.py --city {cityCode}
   python data-pipeline/sync_master_data.py --city {cityCode}

   - master/councilors_{cityCode}.json が定数通り生成されていること。
   - frontend/public/data/{cityCode}_speaker_stats.json が同期されていることを確認する。


-----------------------------------------------------------------------
Phase 3: 議事録データ抽出・質疑スレッド・タイムラインの生成
-----------------------------------------------------------------------

1. 議事録生データの構造プロファイリング
   - 行政側役職キーワードリストを作成し、答弁者を正確に除外・識別する。
   - 首長・副市長・局長等で役職接尾語なしの「苗字単体」で記録されている場合、admin_names リストへ事前登録する。
   - 議員名末尾の「委員」「議員」「君」などの役職サフィックスを除去・正規化してマスターと突合する。

2. 議事進行・採決ノイズフィルタ（procedural_phrases）の実装
   - 委員長・座長発言（「お諮りいたします」「御異議ございませんか」「さよう決定いたします」「これより委員会を開会」「散会いたします」等）をスレッド開始から事前除外する。

3. BigQuery 単一JOINクエリによるデータ抽出
   - conferences -> meetings -> minutes -> conversations を単一クエリで取得し、m.url AS official_url を必ず含める。

4. 質疑・答弁タイムライン分割（build_timeline_contexts.py）
   - 各スレッドの質問開始から答弁終了まで、前後に適切なバッファを持たせて抽出・JSON分割する。

5. 会議録サマリーJSONの生成（generate_static_data.py）
   - フロントエンド用 statements_summary.json を生成する。


-----------------------------------------------------------------------
Phase 4: 議決・賛否データスクレイピング＆AI論点解説
-----------------------------------------------------------------------

1. 議決・賛否データの抽出
   - 直近任期（4年間）の本会議議決一覧から全会一致以外の対立案件を全件抽出し、{cityCode}_votes_summary.json に整形する。
   - 市会だよりCSV等を用いる場合、utf-8-sig / cp932 / shift_jis の自動フォールバック、SESSION_FALLBACK（会期名辞書）、FACTION_MAP（会派・人数略称名寄せ）を適用する。

2. 対立議案AI論点解説パイプライン（generate_bill_issues.py）
   - 対象議案の選定: 賛成と反対が混在する対立議案（contested_bills）のみを対象とする。
   - ストップワード除外: find_context_stmts の正規表現に新都市名を必ず追加（re.sub(r'京都市|大阪市|名古屋市|横浜市|{新都市名}|...', '', title)）。
   - Gemini 2.5 Flash による 4〜8 並列バッチ処理と 429 バックオフリトライ。
   - 出力先: frontend/public/data/{cityCode}_bill_issues.json（8大カテゴリ、key_conflict、background、agree_logic、disagree_logic）。


-----------------------------------------------------------------------
Phase 5: 選挙公報原本物理抽出＆セマンティック公約結合
-----------------------------------------------------------------------

1. 選挙公報PDFの一括アーカイブ・配置
   - 各区選管または国立国会図書館WARPから公式公報原本PDFを取得し、data-pipeline/raw_pdfs/{cityCode}/ に集約する。
   - 命名規則: 市長選は {cityCode}_mayor_{year}.pdf、市議選は ward_{wardName}.pdf。

2. Pydantic構造化出力による物理抽出
   - Gemini 2.5 Flash と Pydantic スキーマ（response_schema）を用いて物理抽出スクリプトを実行する。
   - exact_quote には紙面に印刷された文字テキストをそのまま抜き出す（要約・言い換えは絶対不可）。
   - 確認できないデータは白紙（未転記）とし、ハルシネーションを完全に防止する。

3. 質疑＆公約 Embedding キャッシュの差分生成
   [実行コマンド]
   python data-pipeline/cache_statement_embeddings.py --city {cityCode}

4. 統一公約・採決行動トラッカーのビルド
   [実行コマンド]
   python data-pipeline/build_unified_pledge_tracker.py --city {cityCode}

   - 出力先: frontend/public/data/{cityCode}/pledge_tracker.json。
   - 必ず辞書型（{ "議員名": { "tracked_items": [...] } }）とし、姓名スペース除去キーを同一参照で格納する。


-----------------------------------------------------------------------
Phase 6: 政策論戦マップ＆首長トラッカーの構築
-----------------------------------------------------------------------

1. 政策論戦マップの生成（generate_unified_topic_summaries.py）
   - 新都市の政策論点設定（{CITY}_TOPIC_CONFIGS）をデータドリブンに定義する（一次議事録の頻出キーワードに基づく）。
   - 生発言本文（statement_text）の最優先格納（AI要約文の排除）。
   [実行コマンド]
   python data-pipeline/generate_unified_topic_summaries.py --city {cityCode}

2. 首長政策・予算トラッカーの構築
   - data-pipeline/build_mayor_tracker_{cityCode}.py を作成する。

【トラブルシューティング・チェックリスト（実戦教訓）】
=======================================================================

| 現象 | 主な原因 | 対処法 |
| :--- | :--- | :--- |
| 首長交代サーキットブレーカーが誤爆・停止する | 自治体公式トップのURL変更、または首長交代直後 | `mayors.json` の想定首長名・公式URLを確認し、新首長体制へ更新して再実行する |
| 定数上限サーキットブレーカー（超過）が発動する | 多言語リンク（Language/がいこくご）等のUI文字列が正規表現にマッチした | `is_valid_councilor_name` の除外キーワードを追加し、文字種（日本語必須）・文字数上限（8文字）を適用する |
| 平仮名名義の議員が「未検出」として除外される | 文字数上限バリデーション（len <= 6）が厳しすぎた | 平仮名7文字氏名（例: おさかべさやか）を許容するため文字数上限を「8文字」に設定する |
| スクレイピングで全議員が「無所属」で上書きされる | 会派ページの走査タグに対象構造（`<dl>`, `<dd>`等）が含まれずマップが空になった | 会派パースタグを修正する。また無所属率50%超で既存データを自動維持する「会派充足率ガード」が正しく働くか確認する |
| 京都は生発言なのに新都市は要約文が表示される | `generate_unified_topic_summaries.py` で `summary` を代入していた | `statement_text`（生発言本文）を最優先で取得・格納するよう統一し、定型句をトリムして再生成する |
| 防災トピックに「民泊」など全く無関係な質疑が混入する | キーワードに「津波避難」などの端緒単語が含まれ誤爆した | キーワードを「防潮堤」「浸水想定区域」等の主題複合語に厳格化してトピック生成を再実行する |
| トピック詳細カードをクリックしてもモーダルが開かない | `TopicDetailPage.jsx` が不完全な独自オブジェクトを作って渡している | `SpeakerDetailView` と完全同一の `handleViewExchangeContext`（原本レコード探索）に統一する |
| 発言カードに「西島副首都」などの行政局長名が表示される | 行政理事者の説明・答弁発言が誤って議員質問として抽出された | 局長・理事者の役職名を検知し、同一会議録内の正規議員の質疑レコードへ置換するかカードを除外する |
| 「公式原本で確認」が会議録検索トップに飛ばされる | `officialLink.js` が `source_url` のみを参照し `official_url` を無視していた | `stmt.official_url || stmt.source_url` の優先度チェーンに変更し、MinuteSearchをMinuteViewへ置換する |
| 会議録リンクが 404/403 エラーになる | テナントが誤っている（例: `osaka`）、またはスマホ用 `SpMinuteView` に直リンクしている | テナントは `cityosaka` に修正し、リンクはPC版 `MinuteView.html` に統一する |
| 議員マスタJSONがあるのに会派や行政区が反映されない | `useStatements.js` が配列形式のみを想定し辞書形式のマスタ読み込みをスキップしていた | `starts_with('[')` 単体判定を撤廃し、dict / array の両構造を自動判定して正規化・マージする |
| 新都市の画面に京都市の議員や質疑が表示される | `useStatements.js` が京都のSupabaseをフェッチしている | Supabaseフェッチ条件に `cityCode === 'kyoto'` を追加し、新都市は静的マスタを直読みさせる |
| GitHub Push時に "exceeds 100.00 MB" エラー | Embeddingキャッシュファイル（100MB超）がコミットに含まれている | `git reset HEAD~1` でコミットを取り消し、`.gitignore` に `**/embeddings_*.json` を追記して再コミット |
| 新しい公約を追加したが質疑・採決が紐づかない | 古い公約ベクトルキャッシュ（`embeddings_{city}_pledges.json`）が残っている | 該当都市の公約キャッシュを削除してからビルドを再実行し、最新公約ベクトルを再生成させる |
| BigQueryからのデータ抽出に10分以上かかる | 会議一覧をループして1件ずつクエリしている（N+1問題） | conferences〜conversations を単一クエリで JOIN して一括ロードする |
| 議事進行・採決手続きが政策質疑として抽出される | 委員長・座長を務める議員の発言が質疑として誤判定された | procedural_phrases（お諮りします、決定します等）でスレッド開始から事前除外する |
| 市長や副市長の答弁が質疑スレッドの先頭に混入する | 行政幹部が役職なしの「苗字単体」で記録されている | admin_names（山中、平原、鯉渕等）に幹部名を登録し答弁者判定に含める |
| アダプター更新時に SyntaxError や NameError が発生する | パイプライン本体内に直接コードを注入・置換した | `{city}_adapter.py` を独立ファイルとして作成し、本体からは import する疎結合構成にする |
| 市会だよりCSV取得時に UnicodeDecodeError が発生する | 自治体サイトのCSVが号数によってUTF-8とShift-JIS/CP932で混在している | `utf-8-sig` -> `cp932` -> `shift_jis` の順で try-except デコードするループを設ける |
| 会派名が「民(4)」「国(6)」など略称のまま出力される | 横浜等の市会だより特有の人数付き略称表記になっている | `clean_faction_name()` で括弧内の人数を除去し、`FACTION_MAP` で正式会派名・議員名へ名寄せする |
| `generate_bill_issues.py` で新都市の議事録ログが全くバインドされない | `find_context_stmts` のストップワード除外に新都市名が入っていない | `re.sub` のストップワード正規表現に新都市の正式名称（例: `横浜市`）を追加する |
| `GEMINI_API_KEY が見つかりません` と表示される | APIキーがプロジェクトルートではなく `data-pipeline/.env` に配置されている | `load_env()` を改修し、スクリプト階層の `.env` とルート `.env` の両方を自動探索させる |
| 自治体公式名簿から顔写真が取得できない（特定議員のみ欠落） | 公式HTMLの `img[alt]` が氏名ではなく会派名になっている | `alt` 単体依存を排し、見出し議員名ブロックと直後の紹介枠をペア走査して画像URLを抽出する |

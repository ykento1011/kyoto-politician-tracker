=======================================================================
議会のミカタ：新規都市追加・水平展開 標準運用手順書 (SOP)
改訂: 2026年10月（公約トラッカースキーマ統一・生発言テキスト統一・原本直結モーダル連動・全自動インテグリティ監査標準化・公報原本物理抽出の厳格化）
=======================================================================

【基本原則】

1. 設定駆動（Config-driven）アーキテクチャとProps伝搬の徹底
   - 都市固有の名称・カラー・URL・ファイルパス・SEOメタタグは設定ファイル（`frontend/src/config/cities.js`）および都市アダプターに集約する。
   - コンポーネント内部やユーティリティ関数（リンク生成等）に都市名やテナント名をハードコード（直書き）してはならない。
   - 下層コンポーネントや関数を呼び出す際は、必ず `cityCode` をPropsや引数としてバケツリレー（伝搬）させること。二者択一の三項演算子（例: `isOsaka ? 'osaka' : 'kyoto'`）やデフォルト引数（`='kyoto'`）への甘えは厳禁。
   - すべてのデータJSONのフェッチは `getCityDataUrl(cityCode, 'ファイルキー')` を経由して行う。

2. 一次情報至上主義と会議録ディープリンク完全保証（Zero-Hallucination & Deep Link Gate）
   - 二次解説や推測によるデータ登録を一切禁止し、自治体公式Web・市会公式・選管公式PDF・原本公文書のみを情報源とする。
   - 【厳格追加】LLM等の推論による公約や政策テキストの自動生成・補完・捏造（ハルシネーション）は、いかなる場合も絶対厳禁とする。公約テキストは、専用スクリプトを用いた公式選挙公報PDFからの正確な物理的抽出（OCR/テキストパース）および目視による一言一句違わぬ転記のみを許可し、確認できないデータは「白紙（転記待ち）」とする。
   - 会議録への直リンクは「個別会議・発言のPC版ビュー（MinuteView.html）」を絶対原則とし、検索トップ（MinuteSearch.html / SpMinuteSearch.html）への安易な逃げやハードコードを厳禁とする。
   - スマートフォン版URL（SpMinuteView.html）は外部直接参照時に403エラーを誘発するセキュリティ仕様が存在するため、必ずPC版パーマリンク（MinuteView.html?council_id=...&schedule_id=...）を採用する。

3. 生発言（肉声）優先・三人称要約の根絶原則【超重要・都市間対称性】
   - トピック詳細画面（政策論戦マップ）や発言カードに表示するテキストは、AIによる三人称要約文（「議員は〜について質問し、行政側が〜答弁した」）を排し、タイムライン原本の【議員本人の実際の発言本文（statement_text / 肉声）】を最優先で格納・表示する。
   - 京都・大阪・名古屋など、閲覧する都市によって表示形式（生発言か要約文か）に非対称性・乖離を生じさせてはならない。

4. UIモーダル連携の単一ロジック化・原本レコード直結原則
   - トピック詳細画面（`TopicDetailPage.jsx`）において、手動でプロパティを再構成した不完全なオブジェクトをモーダルに渡してはならない。
   - 議員詳細画面（`SpeakerDetailView.jsx`）や一覧カード（`ThreadCard.jsx`）と全く同一の質疑レコード解決ロジック（`handleViewExchangeContext`）に統一し、原本データベース（`statements_summary.json`）の完全なレコードを `onViewContext(stmt)` に直接引き渡す。

5. 行政理事者（局長・部長等）発言の完全排除と議員質疑への正規化
   - 政治家トラッカーは市民の代表である議員（および市長）を追跡するシステムである。
   - 行政側の局長・理事者（例:「西島副首都」「丸山大阪」「○○局長」等）の答弁・説明発言が単独で「議員質問」としてトピックカードに混入することを厳禁とし、同一会議でその質疑を行った本来の正規議員レコードへ置換、またはカードを除外する。

6. 単一パイプライン・アダプター原則（No-Copy-Paste Pipeline）【厳格遵守】
   - 都市ごとにパイプラインスクリプトを複製（コピペ）することを物理的に禁止する。
   - パイプラインはすべて `data-pipeline/` に集約し、`pipeline/` のような別名フォルダの並立や、場当たり的な一時修復スクリプト（temp_*.py 等）の乱立を禁止する。
   - LLM評価プロンプト、8大政策カテゴリ、4軸整数スコア、キーワード、並列処理は単一の共通コア（run_unified_pipeline.py）で集中管理する。
   - トピック要約（マクロ論戦マップ）も単一の共通ジェネレーター（generate_unified_topic_summaries.py）で集中管理する。
   - 都市ごとの差異（BigQueryクエリ、行政側役職判定、名寄せ、スレッド化ロジック）は「都市アダプター（{City}Adapter）」クラスとしてのみ実装する。
   - 【厳格追加・モジュール分離】都市アダプターをパイプライン本体（run_unified_pipeline.py）内に直接記述・置換することを禁止する。必ず `data-pipeline/{cityCode}_adapter.py` として独立モジュール化し、本体からは `from {cityCode}_adapter import {City}Adapter` でインポートして `ADAPTERS` 辞書に登録する疎結合設計を義務付ける（構文破損・エスケープ事故・NameErrorの防止）。

7. 全自動インテグリティ監査（Automated Integrity Audit）の必須化
   - 手動による目視確認には限界がある。新都市追加・データ更新時は、全トピック・全発言カードおよび公約データを網羅走査する検証スクリプトを実行し、【モーダル到達率 100%】【生発言率 90%以上】【現職公約照合率 100%】【原本引用率 100%】が機械的に証明されるまでデプロイを許可しない。

8. 評価スキーマ・キー互換の完全原則（京都マスター準拠）
   - いかなる都市であっても、以下の仕様を勝手に改変してはならない。
     - 政策カテゴリ: 京都マスターの「8大政策カテゴリ」固定（都市計画・その他等の独自分類禁止）。
     - 4軸スコア: 各1〜5の【整数値（int）】（1.0〜5.0等の小数は禁止）。
     - 分析メモ（キー互換）: フロントエンドとの互換性を保つため、`reasoning` と `scoring_reasoning` の【両方のキー】に同一テキストを二重出力する。
     - 発言順序（Sequence Number）: フロントエンドのタイムライン取得に必須。`sequence_number` プロパティを確実にJSONに含めるか、`id` から抽出できる設計にする。
     - 会議録直通URL（official_url）: BigQueryの `meetings.url` から取得した正規の `MinuteView.html` URLを、発言スレッドおよび要約JSONに漏れなく格納する。
     - キーワード（keywords）: 必須。3件の配列。

9. 公約トラッカー（Pledge Tracker）スキーマの完全対称性原則【新規厳格基準】
   - フロントエンド（`SpeakerDetailView.jsx`）は、議員名をキーとした辞書（Dict/Map）形式（`{ "議員名": { ... } }`）を前提としている。独自形式（List型 `[{ speaker: ... }]` や `{ metadata: ..., councilors: [...] }`）での出力は厳禁とする。
   - スキーマ（プロパティ名）は京都・大阪と完全一致させること：
     - 公約配列キー: `tracked_items`（`pledges` は不可）
     - 公報原文引用: `election_promise.quote`（`exact_quote` や `original_text` は不可）
     - 関連質疑リスト: `council_statements`（配列：`date`, `committee`, `summary`, `speech_id`, `official_url`）
     - 代表質疑: `council_statement`（オブジェクトまたは `null`）
     - 関連議決: `council_vote`（オブジェクトまたは `null`）
   - 氏名の姓名スペース揺れ（全角・半角スペースの有無）による検索空振りを防ぐため、辞書キーには「原名」と「スペース完全除去名」の両方を必ず同一オブジェクトへの参照として登録する。

10. データ破壊コマンドの厳禁（Data Safety First）
    - トラブルシューティング時、未コミットの生成・抽出データが存在する状態で `git checkout -- <file>` や `git reset` 等の破壊的コマンドを実行することを固く禁ずる。変更は必ず退避（Stash / Copy）した上で作業すること。

11. BigQuery 単一JOINクエリ一括取得の原則（N+1クエリの禁止）
    - 会議一覧（meetings）をループして1件ずつ発言（conversations）をクエリする「N+1クエリ」は、通信オーバーヘッドにより取得だけで十数分を浪費するため厳禁とする。
    - `conferences` -> `meetings` -> `minutes` -> `conversations` を一括で `JOIN` する単一クエリを発行し、8〜10万件規模の発言であっても数秒でメモリ上に一括展開する設計を必須とする。

Phase 1: 事前適合性診断と自治体ID・会議録テナントの確定
-----------------------------------------------------------------------

1. 自治体ID（governing_body_id）マスタ
   BigQuery抽出時に用いる公式自治体IDを確認・確定する。
   - 京都市会: 88 / 大阪市会: 532 / 名古屋市会: 958 / 横浜市会: 1249 / 神戸市会: 156

2. 会議録システムとDiscussNetテナント識別子マスタ【超重要】
   NTT-AT DiscussNet系（`ssp.kaigiroku.net/tenant/<テナントID>/`）の正式識別子を厳密に確認する。
   - 京都市会: `kyoto`
   - 大阪市会: `cityosaka`（※`osaka` は無効／404）
   - 名古屋市会: `nagoya`
   - 横浜市会: 独自ドメイン運用（`http://giji.city.yokohama.lg.jp/tenant/yokohama/`）

3. 会議録パーマリンクの動作検証
   - `MinuteView.html?council_id=...&schedule_id=...` 形式でブラウザから外部直アクセスし、セッションエラー（403/404）なく議事録が開くことを確認する。
   - BigQueryの `meetings` テーブルの `url` カラムに、この形式のURLが既に正しく格納されているか確認する。

4. 採決結果（議決データ）公開形式の特定
   - 電子採決（HTMLテーブル形式）: 議員個人の賛否が記録されており、機械的抽出が可能。
   - 起立採決（会派別賛否＋例外ト書き）: 「市会だより」等の会派ごとの賛否テーブルと、造反・退席・除斥議員を例外適用して個人賛否を復元する。

Phase 2: 一次資料Deep Research・公文書検証ゲート【必須品質ゲート】
-----------------------------------------------------------------------

1. 首長公約マニフェスト原本の取得・項目抽出
   - 外部メディアの要約記事ではなく、選挙公報原本または首長公式サイトの政策集のみを採用する。

2. 首長トラッカーのデータ構造とピンポイントURL検証
   - データ構造の確認: マイルストーンが配列（milestones: [...]）か、単一オブジェクト（milestone: {...}）かを必ずプロファイリングする。
   - トップページ逃げの禁止: 沿革一覧や検索トップでお茶を濁さず、対象事象に1対1で合致する公文書URLを特定して結合する。

3. 対立議案・賛否が割れた議案（Contested Bills）の抽出と議決データソースの特定
   - 議決データソースの選定:
     ① BigQuery / DiscussNet: 議案採決テーブルが存在する場合は単一クエリで抽出。
     ② オープンデータ / 市会だよりCSV（横浜方式）: 会議録DBに議決が未格納の場合、自治体公式Webの「議会だより（CSV/テキスト）」から過去全号（任期全期間分）を一括取得・パースする。
   - CSVパース時の必須実装ルール:
     - 文字コード判定: UTF-8-SIG / CP932 / Shift_JIS の順で自動デコードするフォールバックを組み込むこと。
     - セッション名フォールバック（SESSION_FALLBACK）: 初期号や別表でCSV先頭の会期名が欠損している場合に備え、号数と定例会名の対応辞書を必ず保持すること。
     - 会派・無所属略称の正規化マッピング（FACTION_MAP）: 「自(31)」「太(1)」等の略記号をフル名称（「自由民主党横浜市会議員団」「太田正孝」等）に名寄せし、任期途中の会派名変更（例:「民」→「国」）の履歴エイリアスを網羅すること。
     - 一括採決（バンドル議案）のクレンジング: 「●条例A●条例B」のような連結セルは「 / 」で適切に区切り、フロントエンドおよびLLM解析時の視認性を担保すること。   - 直近任期（4年間）の本会議議決一覧から、全会一致以外の案件を全件抽出し {cityCode}_votes_summary.json に整形する。

4. 議員マスタの公式選管・市会名簿照合
   - 市会公式名簿から、現職議員全員の「氏名」「所属会派」「選挙区」を抽出し、名寄せ辞書（`ALIAS_MAP`）を整備する。

5. 選挙公報からの看板政策原本テキスト抽出【厳格化・Pydantic必須】
   - 各区選管または国立国会図書館WARPアーカイブの公式選挙公報原本PDFから、現職議員（および首長）の看板政策を抽出する。
   - 抽出プロセスは、必ず `extract_pledges_gemini_{cityCode}.py` を作成し、**Gemini 2.5 Flash モデル** と **Pydantic スキーマ（`response_schema`）** を用いた構造化JSON出力として実装すること。
   - `exact_quote` プロパティには、紙面の該当枠に実際に印刷されている文字テキストをそのまま抜き出すこと（要約や言い換えは絶対不可）。
   - 抽出結果（`data/{cityCode}_pledges.json`）は必ず目視照合し、紙面に物理的に存在しない推測文脈が混入していないか確認する。確認できないデータは「未転記・白紙状態」とし、ハルシネーションによる埋め合わせを絶対に行わない。

Phase 3: 都市アダプター実装・データ抽出とJSON出力
-----------------------------------------------------------------------

1. 会議録生データの構造プロファイリング
   - 行政側（市長、副市長、局長等）と議員の役職キーワードリストを作成し、答弁者を正確に除外・識別する。
   - 首長・副市長・教育長など行政トップ幹部が役職接尾語なしの「苗字単体」（例: 山中、平原、下田、金高、鯉渕 等）で記録されている場合、議員発言と誤認しないよう `admin_names` ホワイトリストとして事前定義する。
   - 議員名末尾の「委員」「議員」「君」などの役職サフィックスを除去・正規化してマスタ（speaker_stats.json）と突合するロジックを設ける。

2. プレースホルダーJSONの先行配置
   - 開発中、Viteが404 HTMLを返してアプリがクラッシュするのを防ぐため、空の配列 [] または空の辞書 {} を事前に配置する。   - 開発中、Viteが404 HTMLを返してアプリがクラッシュするのを防ぐため、空の配列 `[]` または空の辞書 `{}` を事前に配置する。

3. 議事進行・採決ノイズフィルタ（procedural_phrases）の実装【必須】
   - 議員が委員会等の委員長・座長を務めている場合、その議事進行発言が「政策質疑」として誤判定されるのを防ぐ。
   - 「お諮りいたします」「御異議ございませんか」「さよう決定いたします」「一括議題に供します」「これより委員会を開会」「散会いたします」「説明を求めます」「起立を求めます」等の定型進行フレーズで始まる発言をスレッド開始から事前除外する。

4. 都市アダプターの実装（`run_unified_pipeline.py` 内）
   - `fetch_data()`: BigQueryクエリで必ず `m.url AS official_url` を取得すること。
   - `build_threads()`: 各スレッドには質問開始発言の `sequence_number` と `official_url` を漏れなく出力すること。

5. 質疑・答弁タイムラインの生成（`build_timeline_contexts.py`）
   - 各スレッドの質問開始から答弁終了まで、最大12発言程度のバッファを持たせて抽出。

6. 統一トピック要約（政策論戦マップ）の生成（`generate_unified_topic_summaries.py`）
   - 生発言本文の優先格納: `summary` ではなく `statement_text` から挨拶等の定型句をトリムしてカードテキストに格納する。
   - トピックキーワード誤爆の防止: 「津波避難」単体ではなく「津波避難ビル」「防潮堤」等の複合語でスコアリングし、無関係な質疑の混入を防ぐ。

7. 公約トラッカー結合パイプライン（`build_pledge_tracker_{cityCode}.py`）の実行
   - 原本公約データ（`exact_quote`）と、各議員本人の議会質疑（`statements_summary.json`）をキーワード・カテゴリで照合バインドする。
   - 出力は必ず `{ "議員名": { "tracked_items": [...] } }` の辞書形式とし、原名およびスペース除去名の両キーを格納する。

8. 全件バッチ実行前のサンプリング品質監査ゲート（--limit 10）【必須】
   - 数千件規模の全件バッチを実行する前に、必ず `--limit 10` でサンプリング実行を行う。
   - 出力されたチェックポイント（pipeline/{cityCode}_eval_checkpoint.json）を読み込み、以下を目視監査する：
     ① 成果強調表現（「前向き」「鋭い」等）や減点評価語（「至らなかった」「不十分」等）が排除されているか
     ② 参照公文書名、条例条文、具体的数値が「事実メモ（reasoning）」に客観的に抽出されているか
     ③ 4軸スコア（根拠・対案・地域・展開）が実態に応じた適正な分散を示しているか
   - 監査合格後に `--limit` を外して全件バッチを実行する。

9. 対立議案AI論点解説パイプライン（generate_bill_issues.py）の運用標準
   - 対象議案のフィルタリング:
     全会一致（unanimous）の案件は除外し、各会派の賛否が分かれた対立議案（contested_bills: 賛成と反対が混在）のみを抽出してAI解説を生成する。
   - 形態素・ストップワード除外:
     議事録発言ログ（statements_summary.json）とのキーワード結合時、新都市名を必ずストップワード除去正規表現（re.sub(r'京都市|大阪市|名古屋市|{新都市名}|...', '', title)）に追加し、都市名ヒットによる誤爆を防止する。
   - 環境変数探索の堅牢化（Multi-path .env Load）:
     実行コンテキストの差異を吸収するため、スクリプト所在ディレクトリ（data-pipeline/.env）、プロジェクトルート（.env）、カレントディレクトリの順でGEMINI_API_KEYを探索・読み込む設計とする。
   - 並列処理と中断レジューム（チェックポイント保存）:
     Gemini 2.5 Flash モデルを使用し、ワーカー数は 4〜8 並列で実行する。APIクォータ超過（429 / RESOURCE_EXHAUSTED）時は指数バックオフ（Exponential Backoff）でリトライし、5件完了ごとおよび全完了時に中間成果物を自動永続化する。
   - スキーマ完全準拠:
     出力先は `frontend/public/data/{cityCode}_bill_issues.json` および `dist/data/` とし、8大政策カテゴリ、key_conflict（30字以内）、background、agree_logic、disagree_logic の各キー欠損率を0件とする。

| 議員マスタJSONがあるのに会派や行政区が反映されない | `useStatements.js` が配列（`[`）形式のみを想定し、辞書（`{`）形式のマスタ読み込みをスキップしていた | `starts_with('[')` 単体判定を撤廃し、dict / array の両構造を自動判定して正規化・マージするロジックにする |
| 自治体公式名簿から顔写真が取得できない（特定議員のみ欠落） | 公式HTMLの `img[alt]` が氏名ではなく会派名になっていた、または画像と氏名が別テーブル・別DIVに分離している | `alt` 単体依存を排し、`<h3>` 議員名ブロックと直後の紹介枠（`.shokai_wp` 等）をペア走査して画像URLを抽出する |
| 名古屋市会議員が全員「無所属」と表示される | `speaker_stats.json` が「無所属」で初期化され、マスタのキー名が `party` ではなく `faction` になっていた | マスタの正規会派データをJSONに同期し、アダプター層で `faction` を `party` / `partyGroup` にマッピングして返却する |
